# Alertmanager checks

Everything reported about the `alertmanagers:` block in `ruler.yaml`: where
alerts are posted, and the credential used to post them.

The block is operator owned, in the same file and the same CODEOWNERS lane as
the sources. An Alertmanager is an operator concern in the way a cluster is: a
team that wants to bring its own needs the operator to agree, to hold its
credential and to let the network reach it. See spec 6.5.

`alertmanager/url`, `alertmanager/auth` and `alertmanager/tls` are fixed at
`error`. A URL that will not parse, a credential that cannot be read and a CA
bundle that cannot be read are the same failure, which is that no page can be
delivered, and there is nothing for policy to soften.
`alertmanager/tls-insecure` is configurable, because an exemption is what
clears it.

## Where alerts go

<a id="alertmanager-url"></a>

### alertmanager/url

An Alertmanager URL that will not parse, carries a credential, or is named
twice.

Three things make a URL malformed, and each is one no send could ever succeed
against: no scheme, a scheme `net/http` will not speak, or no host to send to.
Reachability is not one of them, because that needs the network and changes
while the ruler runs. `clickhouse_ruler_alertmanager_last_probe_successful`
answers reachability instead.

```yaml
# before: builds localhost:9093/api/v2/alerts, which net/http refuses at the
# first send, possibly hours later
alertmanagers:
  - urls: [localhost:9093]

# after
alertmanagers:
  - urls: [http://localhost:9093]
```

**A URL carrying userinfo is refused.** Go's `http.Client` turns userinfo into
an `Authorization: Basic` header, so it would authenticate, which is exactly
why it is refused rather than ignored: a password in a URL is in the pod spec,
in the rendered chart manifest, and in any dump that echoes argv, where no
amount of redaction reaches it. The finding names the field to use instead.

```yaml
# before
alertmanagers:
  - urls: [http://ruler:hunter2@alertmanager:9093]

# after
alertmanagers:
  - urls: [http://alertmanager:9093]
    basic_auth:
      username: ruler
      password_file: /run/secrets/ruler/alertmanager
```

**The same URL twice is refused.** It is one page posted twice to one member,
which Alertmanager deduplicates, so nothing breaks and nothing is gained. What
it does break is the metrics: the `alertmanager` label is the URL, so two
identical values are one series and a failure counter would report two
endpoints as one. Deduplicating quietly would leave an operator with a list
that does not describe what the ruler is doing.

List each member of the cluster once. Every alert is posted to every member,
which is what Alertmanager's own clustering documentation asks for, and a
balancer in front of them is not.

<a id="alertmanager-auth"></a>

### alertmanager/auth

A credential that could not be read, or both credential sources set at once.

The names are Prometheus' own, because an operator configuring an Alertmanager
has written them before: `basic_auth` with `username`, and `authorization`
with `type` for the bearer token case.

The secret itself is never written in the file. It comes from a file or from
the environment, which is the posture the sources already take, and the same
refusals apply. `password_file` and `password_env` are mutually exclusive
rather than ordered by precedence, as are `credentials_file` and
`credentials_env`: when the two disagree one of them is stale, and silently
picking either can authenticate with a credential that was supposed to have
been rotated away. An empty file is reported too, because a projected secret
volume that has not populated yet reads as one.

```yaml
# before: which one is current?
basic_auth:
  username: ruler
  password_file: /run/secrets/ruler/alertmanager
  password_env: RULER_ALERTMANAGER_PASSWORD

# after
basic_auth:
  username: ruler
  password_file: /run/secrets/ruler/alertmanager
```

Setting both `basic_auth` and `authorization` on one set is refused for the
same reason: they write the same `Authorization` header, so one of them would
silently win.

**Prefer `password_file`.** A reload re-reads it, so a rotated secret is
picked up by `SIGHUP`. A process cannot change its own environment, so
`password_env` is only rotated by a restart, and a restart makes every pending
alert serve its `for` again.

No credential at all is fine, and is what the compose stack runs: an
Alertmanager on a network only the ruler can reach does not need one.

## Reaching it over TLS

<a id="alertmanager-tls"></a>

### alertmanager/tls

TLS key material that could not be read, or a `tls_config` that reaches no
`https` URL.

The five fields are Prometheus' own, and they are the five a source already
takes: `ca_file`, `cert_file`, `key_file`, `server_name` and
`insecure_skip_verify`. One reader reads both blocks, so the refusals and the
wording are the same on either.

```yaml
alertmanagers:
  - urls: [https://alertmanager:9093]
    tls_config:
      ca_file: /run/secrets/ruler/alertmanager-ca.pem
      cert_file: /run/secrets/ruler/alertmanager.pem
      key_file: /run/secrets/ruler/alertmanager-key.pem
```

**The scheme turns TLS on, and a `tls_config` beside a plaintext URL is
refused.** A source has `secure:` and this block does not, because an endpoint
is a URL and `https://` already says it. So material no member of the set can
reach is a contradiction rather than a precedence rule: the ruler would post in
plaintext while a reviewer reads a file that names a CA.

```yaml
# before: the CA is never reached
alertmanagers:
  - urls: [http://alertmanager:9093]
    tls_config:
      ca_file: /run/secrets/ruler/alertmanager-ca.pem

# after
alertmanagers:
  - urls: [https://alertmanager:9093]
    tls_config:
      ca_file: /run/secrets/ruler/alertmanager-ca.pem
```

Every member of the set, not one of them. The set is one cluster sharing one
client, so members that disagree about their transport are a mistake in the
file.

**`ca_file` replaces the host's trust store rather than adding to it.** The CA
that signed your Alertmanager becomes the only thing that can vouch for it, so
a public CA that mis-issues a certificate for the same name is not trusted for
this connection. An Alertmanager behind a public CA names no bundle at all and
gets the host's trust store, which is what `https://` on its own means.

**`cert_file` and `key_file` go together.** A certificate with no key cannot be
presented and a key with no certificate is never sent, which reads as an
Alertmanager refusing a credential that was never offered. The pair is checked
for being a pair when the file is parsed, so half a rotation is a finding in
front of whoever changed the file rather than a handshake failure at an
arbitrary hour.

**Set `server_name` when the URL is not the name on the certificate**, which is
an IP address or a tunnel. Left out, the host in the URL is what is verified.

**What a reload does, and what it does not.** This is the part worth knowing
before a certificate rotation is due:

| Replaced on disk | What picks it up | What you do |
|---|---|---|
| `cert_file`, `key_file` | the next handshake | nothing |
| the credential's `password_file` or `credentials_file` | a reload | `SIGHUP`, or `POST /-/reload` |
| `ca_file`, or any edit to `tls_config` | a restart | restart the ruler |
| `urls` | a restart | restart the ruler |

The client pair is read inside the handshake, so a certificate manager rotating
it on its own schedule needs nothing from you. The CA is held as the bytes that
were read, because the roots live inside a built HTTP transport: applying a new
bundle means replacing that transport while sends and probes are using it,
which a reload does not do. A reload that reads different material logs that it
needs a restart and keeps the endpoints already running, so an edit that did
nothing says so rather than looking applied.

A restart is not free, which is why it is said out loud: every pending alert
serves its `for` again, and resolves being retried are forgotten. Plan a CA
rotation the way you would plan a version bump.

All of these are `error` and all of them refuse the start, because an
Alertmanager this ruler cannot reach is every alert in the checkout rather than
one rule behaving as written. The exception is the check below.

### alertmanager/tls-insecure

An Alertmanager reached with certificate verification off and no exemption.

`insecure_skip_verify: true` keeps the connection encrypted and stops anything
identifying the server at the other end of it. The pages still arrive; what is
gone is any guarantee about who they arrive at.

It is an error that an exemption clears, with a reason and a date, which is
`source/tls-insecure`'s design one block over:

```yaml
alertmanagers:
  - urls: [https://alertmanager:9093]
    tls_config:
      insecure_skip_verify: true
    exempt:
      - check: alertmanager/tls-insecure
        reason: the alertmanager is self-signed until the internal CA lands
        until: 2026-12-01
```

`until` is the first instant no longer covered, so `2026-12-01` covers November
and not December, and a bare date is midnight UTC wherever the check runs. On
the day it expires the file fails CI under `source/exemption` and renewing it
means stating the reason again in front of a reviewer.

**It does not refuse the start, and it is the only `alertmanager` check that
does not.** The delivery path works, so this is a finding: it blocks a merge,
it is raised on `clickhouse_ruler_problem` while the ruler runs, and it is
fixed by a pull request in office hours. Refusing instead would turn the expiry
date into a landmine armed to your next restart: the running ruler pages on
past the date, and then a node drain or an image bump at three in the morning
finds a pod that will not start and an estate with no alerting at all, over a
calendar entry.

What to reach for first is a `ca_file` naming the CA that signed the
Alertmanager, which is one line and needs no exemption. Reach for this when you
do not have that bundle yet.
